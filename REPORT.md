# Итоговый аналитический отчет (Лабораторная работа №1)

## 1. Резюме (Executive Summary)
Проект: микросервис «Расчет корзины и скидок» для системы лояльности.
В работе выбрана СУБД (PostgreSQL по взвешенной матрице решений),
настроен репозиторий с ветвлением main/develop/feature, защитой develop
и CODEOWNERS, подключён CI-контроль качества (flake8 + GitHub Actions),
выполнено обратное проектирование legacy-алгоритма расчёта корзины
(диаграмма деятельности) и подготовлен план code-review.

## 2. Сравнительный анализ технологий

### 2.1. Матрица принятия решений
| Критерий | Вес | PostgreSQL | MongoDB |
|---|---|---|---|
| Поддержка ACID-транзакций | 0.35 | 5 | 3 |
| Производительность чтения | 0.20 | 4 | 5 |
| Экосистема и инструменты | 0.20 | 5 | 4 |
| Гибкость схемы | 0.15 | 3 | 5 |
| Стоимость владения | 0.10 | 5 | 3 |
| **Сумма весов** | **1.00** | | |

### 2.2. Расчёт и обоснование выбора
Формула: Оценка = Σ (Вес_критерия × Балл_кандидата)

**PostgreSQL:**
0.35×5 + 0.20×4 + 0.20×5 + 0.15×3 + 0.10×5
= 1.75 + 0.80 + 1.00 + 0.45 + 0.50 = **4.50**

**MongoDB:**
0.35×3 + 0.20×5 + 0.20×4 + 0.15×5 + 0.10×3
= 1.05 + 1.00 + 0.80 + 0.75 + 0.30 = **3.90**

**Вывод:** побеждает PostgreSQL (4.50 против 3.90). Для баллов,
транзакций и промокодов критична целостность данных: ACID и строгие
ограничения (constraints) снижают риск потери или двойного списания
баллов, поэтому критерий ACID получил наибольший вес. Гибкость схемы
у MongoDB удобна, но для финансовых данных вторична; в PostgreSQL
недостающую гибкость частично закрывает тип JSONB.

## 5. Обратное проектирование и планирование ревью

### 5.1. Анализ алгоритма
<img width="499" height="917" alt="image" src="https://github.com/user-attachments/assets/8598edb8-eab4-49cb-9faf-6de26df12250" />


Выявленные «запахи кода» (Code Smells):
1. **Магические числа:** 15000, 0.85, 500, 0.90, 0.97, 0.93, 0.70.
2. **Магические строки:** "SUMMER", "VIP", коды уровней 1 и 2.
3. **Нет валидации входных данных:** отрицательная сумма, tier не из
   списка, promos = None.
4. **Нет защиты от повторов промокодов:** ["VIP", "VIP"] применит
   скидку дважды (риск фрода).
5. **Результат зависит от порядка промокодов:** вычитание 500 до/после
   умножения даёт разный итог.
6. **Деньги в float:** ошибки округления, нет округления результата.
7. **Длинная цепочка if/elif:** при добавлении промокодов и уровней
   функция будет расти (нарушение принципа Open/Closed).
8. **Отсутствуют докстринг, типы и тесты.**
9. **Мутация одной переменной price:** сложно читать и отлаживать.
10. **Одна функция делает всё:** база, промокоды, лояльность и лимит.

### 5.2. План code-review
Подход: ревью каждого изменения src/discount.py через PR с
обязательным аппрувом владельца кода; проверка по чек-листу критериев.
Открытый PR: https://github.com/xadixadovich/lab1-comprehensive-M.Vorobyev/pull/3

Ключевые измеримые критерии: 0 магических чисел, валидация входных
данных, покрытие тестами > 80%, 0 ошибок flake8.
Эскалация: обсуждение в PR (до 2 итераций) → решение Tech Lead
за 1 рабочий день → по бизнес-правилам решает владелец продукта.

## 6. Заключение
Настроенные процессы снижают риск дефектов на нескольких уровнях:
защита develop и CODEOWNERS исключают прямые коммиты без ревью;
flake8 в CI автоматически блокирует очевидные ошибки до слияния;
взвешенный выбор СУБД учитывает критичность целостности финансовых
данных; план ревью и анализ code smells фиксируют, что именно
проверять в расчёте скидок.
